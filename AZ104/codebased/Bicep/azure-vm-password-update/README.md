# Azure VM Password Rotation with Bicep + Azure Key Vault

## Objective

This demo assumes that you already have:

- An **existing Azure VM**
- An **existing Azure Key Vault**
- A **service principal / deployment identity**
- Permission for that identity to:
  - update/reset the VM account password
  - create/update a Key Vault secret

The goal is:

```text
              Deployment / Service Principal
                         |
                         | 1. Generate complex password
                         v
                  Secure Bicep parameter
                         |
              +----------+-----------+
              |                      |
              v                      v
       Existing Azure VM       Existing Key Vault
              |                      |
              | 2. Reset password    | 3. Store secret
              v                      v
       admin account            VM password secret
```

The password is generated for the deployment, used to reset the existing VM account, and stored in Key Vault for future retrieval.

---

# Important design point

**Bicep itself is not the ideal place to generate a cryptographically random password.**

Bicep can generate deployment values such as `newGuid()` / `uniqueString()`, but these should not be treated as a password generator.

For a real password-rotation workflow, generate the password in the deployment script or CI/CD pipeline using a cryptographically secure generator and pass it to Bicep as a **secure parameter**.

Example:

```bash
openssl rand -base64 48
```

Then pass that value to Bicep using:

```bash
--parameters generatedPassword="$PASSWORD"
```

The Bicep template in this demo uses:

```bicep
@secure()
param generatedPassword string
```

This is intentional.

# What the Bicep template does

The template references the VM as an **existing resource**:

```bicep
resource vm 'Microsoft.Compute/virtualMachines@2024-07-01' existing = {
  name: vmName
  scope: resourceGroup(vmResourceGroup)
}
```

It also references the existing Key Vault:

```bicep
resource keyVault 'Microsoft.KeyVault/vaults@2024-11-01' existing = {
  name: keyVaultName
}
```

It does **not** create a new VM or a new Key Vault.

# Step 1 — Generate a strong password

Linux/macOS:

```bash
PASSWORD=$(openssl rand -base64 48)
```

You can inspect it during a lab:

```bash
echo "$PASSWORD"
```

For production automation, avoid printing it.

A stronger example with explicit character requirements can be generated by your CI/CD system or password-generation utility.

---

# Step 2 — Verify Azure login

The service principal should be the identity executing the deployment.

For example:

```bash
az login --service-principal \
  --username "<CLIENT_ID>" \
  --password "<CLIENT_SECRET>" \
  --tenant "<TENANT_ID>"
```

Or, if using a certificate:

```bash
az login --service-principal \
  --username "<CLIENT_ID>" \
  --certificate /path/to/service-principal.pem \
  --tenant "<TENANT_ID>"
```

Then verify:

```bash
az account show
```

> Do not put the client secret or private key into the Bicep file.

---

# Step 3 — Permissions required

The deployment identity needs permission to modify the VM and write the Key Vault secret.

## Key Vault

If the vault uses Azure RBAC, a common role for this demo is:

```text
Key Vault Secrets Officer
```

This allows secret management operations.

Check the role assignments:

```bash
az role assignment list \
  --scope "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<KV_RESOURCE_GROUP>/providers/Microsoft.KeyVault/vaults/<KEYVAULT_NAME>" \
  --assignee "<SERVICE_PRINCIPAL_OBJECT_ID>" \
  --output table
```

For a production environment, use the least-privilege role appropriate for your deployment.

## VM

The deployment identity also needs sufficient permission to execute the VM Run Command.

A role such as:

```text
Virtual Machine Contributor
```

may be used for a lab, although production environments should use the narrowest permissions that satisfy the workflow.

# How the password reaches the VM

The Bicep template uses:

```bicep
resource resetPassword 'Microsoft.Compute/virtualMachines/runCommands@2024-07-01' = {
```

For Linux:

```bash
printf "%s:%s\n" "${adminUsername}" "${generatedPassword}" | chpasswd
```

For Windows:

```powershell
net user "<username>" "<password>"
```

The Run Command executes inside the existing VM.

---

# How the password reaches Key Vault

The same secure parameter is used by the Key Vault secret:

```bicep
resource vmPasswordSecret 'Microsoft.KeyVault/vaults/secrets@2024-11-01' = {
  name: secretName
  parent: keyVault
  properties: {
    value: generatedPassword
  }
}
```

Therefore:

```text
Generated password
       |
       +--------------------+
       |                    |
       v                    v
Run Command              Key Vault
       |                    |
       v                    v
VM account password       Secret
```

The secret name defaults to:

```text
<VM_NAME>-admin-password
```

You can override it:

```bash
--parameters secretName="prod-vm-admin-password"
```

# Step 7 — Verify the Key Vault secret

List the secret:

```bash
az keyvault secret show \
  --vault-name <KEY_VAULT_NAME> \
  --name <SECRET_NAME> \
  --query id \
  --output tsv
```

Retrieve the value when authorized:

```bash
az keyvault secret show \
  --vault-name <KEY_VAULT_NAME> \
  --name <SECRET_NAME> \
  --query value \
  --output tsv
```

For example:

```bash
PASSWORD_FROM_KV=$(az keyvault secret show \
  --vault-name <KEY_VAULT_NAME> \
  --name <SECRET_NAME> \
  --query value \
  --output tsv)
```

Do not echo the variable in production automation.

# Important security consideration

There are two separate operations:

### Operation 1

Change the password on the VM.

```text
VM Run Command
      ↓
local account password changed
```

### Operation 2

Store the same password.

```text
Key Vault
   ↓
secret created/updated
```

The deployment identity must therefore have permissions for both operations.

# Password rotation

This same template can be used for rotation.

Example:

```text
Existing password
       ↓
Generate NEW password
       ↓
Bicep deployment
       ↓
Reset VM password
       ↓
Update Key Vault secret
```

Run the deployment again with a newly generated password:

```bash
PASSWORD=$(openssl rand -base64 48)

az deployment group create \
  --resource-group <VM_RESOURCE_GROUP> \
  --template-file main.bicep \
  --parameters \
      vmName="<VM_NAME>" \
      vmResourceGroup="<VM_RESOURCE_GROUP>" \
      keyVaultName="<KEY_VAULT_NAME>" \
      adminUsername="<ADMIN_USERNAME>" \
      osType="Linux" \
      generatedPassword="$PASSWORD"
```

The Key Vault secret is updated with the new value.

---

# Important: avoid password exposure

Do **not** do this:

```bash
echo "$PASSWORD"
```

in production.

Do not:

- commit the password to Git
- put the password directly in `.bicep`
- put the password in a normal parameter file
- output the password from Bicep
- print the password in a CI/CD log
- store the password in shell history
- pass it through an unprotected artifact

Use:

```bicep
@secure()
param generatedPassword string
```

and a secure CI/CD secret mechanism.

# Recommended production architecture

For production, use:

```text
                    CI/CD Pipeline
                          |
                          | Managed identity /
                          | Service Principal
                          |
                 +--------v--------+
                 | Password        |
                 | Generator       |
                 +--------+--------+
                          |
                    Secure parameter
                          |
              +-----------+-----------+
              |                       |
              v                       v
       Azure VM                  Azure Key Vault
              |                       |
       Run Command                Secret
              |                       |
              v                       v
       New VM password       Recovery/reference
```

An even stronger architecture is to avoid long-lived VM passwords entirely and use:

- Azure Bastion
- SSH keys
- Microsoft Entra ID login
- Managed identities
- Just-in-time access
- Key Vault only where a password is genuinely required

---

# Key learning points for the demo

1. Existing resources can be referenced using `existing` in Bicep.
2. Bicep can update resources without recreating them.
3. VM Run Command can execute password-reset commands inside an existing VM.
4. `@secure()` should be used for password parameters.
5. Key Vault can store the resulting secret.
6. The deployment identity needs appropriate VM and Key Vault permissions.
7. Bicep should not be treated as a cryptographic password generator.
8. Password generation should happen in a secure deployment environment.
9. The same pattern can implement password rotation.
10. For production, passwordless authentication is generally preferable where supported.
